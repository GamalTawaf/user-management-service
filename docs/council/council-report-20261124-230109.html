Council Report

Prior Authorization API — Project Plan · 2026-11-25 · 5 advisors + peer review + chairman

The question

Pressure-test this senior take-home plan ($180–200K prior-auth API): where will it fail the submission or 45-minute walkthrough, and what should change before coding?

Chairman’s verdict

Where the council agrees

  • Boring stack is fine — FastAPI / Postgres / Alembic / JWT / Compose. Don’t re-litigate tools.
  • Highest risk: thin submitted | in_review | decided without explicit claim, finalize, and actor invariants.
  • Failed intake must be a queryable Support artifact, not only a 422 response body.
  • Cut outbox / wishlist until MVP is solid; Idempotency-Key is commit-or-defer, not half-optional.
  • Before code: state machine + audit matrix + visibility matrix; concurrent claim is non-negotiable.
  • Live session needs a 5-command demo a stranger can run from the README.

Where the council clashes

  • Expansion vs cut: keep Idempotency-Key / actor-shaped OpenAPI / outbox seam as senior signal vs treat them as resume padding. Chairman sides with cut/defer until MVP rules are green.
  • Repo blocker: Executor wants private repo first; Contrarian says start locally now. Both right: code locally today; private template before push/submit.
  • units > 30: hard reject is fine if README defends “almost always typo → hard reject for MVP clarity” in one sentence.

Blind spots the council caught

  • DB constraints must enforce decided ⇒ actor and atomic claim — pytest alone is not enough.
  • Audit payloads can become a PHI leak path if member serializers aren’t designed against them.
  • Need an hour budget / fail-closed list when time runs short.
  • README glossary is the async grader; jargon without definitions fails inheritance.
  • Fake JWT auth threat model (role escalation / forged claims) is under-specified.

The recommendation

Keep the MVP spine and stack. Reorder the plan around three pre-code artifacts: (1) transition graph with claim + whole-request finalize + actor invariants, (2) durable failed-intake records for Support, (3) per-role visibility/redaction matrix. Cut outbox/wishlist; defer Idempotency-Key. Prefer one resource API + RBAC over router-per-actor theater. Collapse six phases into three vertical slices. Encode invariants in schema and write audit in the same transaction as state changes.

One thing to do first: Write a one-page state machine + audit matrix + visibility matrix (including Support lookup by correlation id) into README Decisions — then scaffold only against that page.

Advisor responses

The Contrarian downside
Architecture theater over inheritance. Cut Idempotency-Key and outbox until required by the brief. Thin status enum collapses claim/decide/finalize — fatal under interrogation. Failed intake with no durable row fails Support. Hard units>30 needs a one-sentence defense. Add sequence diagram, redaction matrix, Support path, concurrent-claim as non-negotiable.
The First Principles Thinker strongest
Real bar: can a stranger defend a durable prior-auth state machine under audit in 45 minutes? Four truths only: request transitions + actor, append-only why, hard redaction boundary, findable failed intake. Folders/outbox/idempotency are costume. Before coding: one-page state machine + audit matrix + visibility matrix. Cut any phase that doesn’t force one of those three true.
The Expansionist upside
Win = inheritance theater done right. Make audit + partner OpenAPI the hero path. First-class Support failed-submissions, typed errors, claim race + COI as live demo spine, actor-shaped contracts, keep Idempotency-Key, wire outbox stub and auditor seam for cheap polish. Cut anything that doesn’t narrate durability for teammate / partner / compliance.
The Outsider fresh eyes
Plan assumes prior-auth fluency. IntakeRejection vs request and status names aren’t obvious — if Support lookup lives only in your head, you look junior. Cut wishlist/outbox; commit-or-cut Idempotency-Key; prefer one resource API + RBAC. Add glossary, curl-demonstrable seed story, English audit-per-step, 5-command live script.
The Executor monday
Plan is shippable. Private repo needed to submit; code can start locally now. Draw the transition table; claim with UPDATE … WHERE claimed_by IS NULL; cut outbox; three merges not six phases; one router package. Monday: compose + Alembic + OpenAPI stub + red test for units>30 + clock.py for America/New_York. Anything not demoable from README in 45 minutes is overbuild.
Peer review highlights
4/5 reviewers picked First Principles (D) as strongest. 4/5 flagged Expansionist (A) as biggest blind spot (keeps padding, skips thin status). Shared misses across all advisors: DB-enforced invariants, hour budget / fail-closed list, PHI in audit payloads, fake-JWT threat model, README as async grader.
